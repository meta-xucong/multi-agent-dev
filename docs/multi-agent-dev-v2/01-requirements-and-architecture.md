# multi-agent-dev V2：需求与架构决策

状态：开发前设计冻结候选稿  
版本：V2.0-DRAFT  
适用范围：Codex 多 Agent 协作开发 Skill  
目标包：skills/multi-agent-dev-v2/

## 1. 目标

V2 在保留范围约束、持续纠偏、唯一写入者、独立审计和证据放行的前提下，按职责和任务风险分配模型与推理强度，减少不必要的高强度思考、重复调查和返工。

成功标准：

1. 任务范围、非目标、项目约束和用户硬约束在执行前可查、可冻结。
2. 角色选择、模型/推理档位和升级理由有明确映射，不靠 Agent 临场猜测。
3. Hook 在支持且实测通过的路径上能纠正或拒绝错误派发；Hook 不可用时有能工作的降级路径。
4. 实际模型路由的可验证程度如实报告；收据、配置或 Agent 自述不冒充实际运行凭证。
5. 最终审计基于固定版本、要求原文和可复现证据；不合格后按授权范围修正或补证并复审。
6. 长期观察 V2 是否在质量不退化的前提下减少 Token、无效升级和重复工作；这是后续效率目标，不是首轮技术放行门槛。没有配对实测前不宣称已达到，也不承诺节省比例。

## 2. 规则优先级

冲突时依次服从：

1. 用户本轮最新明确要求与授权。
2. 目标项目的 AGENTS.md、开发文档、契约、章节门禁及安全规则。
3. 本 Skill 已冻结的 V2 需求与验收。
4. V2 支持文档。
5. Agent 的一般建议。

本 Skill 不扩大项目范围，不改变用户的实现方法限制，也不授权提交、推送、部署、真实 Provider 调用、付费操作或外部系统变更。项目规则要求来源追溯时，执行者须先定位固定来源和原实现；来源缺口不得靠 V2 自行补造业务语义。

## 3. 保留、替换与不做

### 3.1 从 V1 保留

- 四种逻辑职责：主控、按需思考、执行、独立审计；不要求四个 Agent 常驻。
- 先读项目规则与开发文档，建立工作区基线，冻结目标、非目标、约束和验收。
- 唯一写入负责人；交接前确认旧写入者停止且没有进行中的写入。
- 小步执行和持续纠偏；越界或依据不足时暂停受影响路径并提交具体问题。
- 审计员只读；结论为“符合 / 不符合 / 证据不足”。拒收后修正或补证、冻结新版本、重审。
- 不检查隐藏推理；通过差异、符号、测试和行为证据检查过度开发与硬约束。
- 按条件启用 context-lean，正式任务默认安静，仅在阶段交接、阻断、变化和终态汇报。
- 任务终态通过 ServerChan 发通知，不在 Codex 主屏输出机器终态标记。

### 3.2 V2 替换

- 用设计歧义、实现难度、审计风险三个维度替代单一 SIMPLE/ESCALATE 二分法。
- 用固定角色路由表作为常规派发策略；Hook 作为可选纠错与拦截层，不作为启动任务的必要依赖。
- 将配置中的模型、派发输入、Hook 修正结果和实际运行元数据分开记录。
- 将“任务功能是否通过”和“模型路由是否得到证明”分成两个结论。

### 3.3 非目标

- 不实现自动切换正在运行的主会话模型。
- 不设每项任务都运行的难度评估 Agent。
- 不要求每次派发重新执行全套 Hook 运行时探针；配置或版本变化时重验，日常记录本次可得的实际元数据。
- 不把 Hook 扩展成通用代码审查器、文件系统安全沙箱或语义理解器。
- 不保证 Skill 能从任意派发路径强制模型、推理强度、工具权限或子 Agent 停止状态。
- 不用 Token 指标放宽项目测试、来源追溯、审计或用户硬约束。

## 4. 逻辑职责

| 职责 | 责任 | 权限边界 | 是否常驻 |
| --- | --- | --- | --- |
| 主控 | 读规则、建立基线、冻结契约、分配档位、维护唯一写入者、纠偏、集成和交付 | 不擅自扩范围、改变硬约束或代替审计员放行 | 当前会话承担 |
| 思考 | 只读澄清需求、来源语义、架构、契约和验收歧义；给出最小决策、选项与风险 | 不写代码/测试、不把建议当授权、不要求隐藏推理 | 按需启用 |
| 执行 | 按冻结契约修改唯一写入边界并做定向验证 | 不改公共语义、不扩功能、不改验收标准；遇设计问题先停相关路径 | 需要具体实现时启用 |
| 审计 | 对固定版本独立检查范围、实现方式、行为、测试和证据 | 不改被审对象，不自修/自补证后自批 | 每次需要验收的实现均独立启用 |

任务过小、委派成本高时，主控可以兼任执行，但审计仍须由作者之外的独立责任人完成。若平台不能提供独立审计 Agent，只能报告自检，不得冒称独立审计通过。

## 5. 三轴分流规则

主控在首次派发前记录三项判断及简短事实依据，不生成长篇推理记录。

### 5.1 设计歧义 D

- D0：用户目标、来源、实现方法、契约和验收均明确。跳过思考 Agent。
- D1：存在会改变实现方向、公共语义、来源适配或验收口径的真实歧义。先启用思考 Agent，只处理该歧义。

“任务较大”本身不是 D1；局部实现困难不自动触发 Sol。

### 5.2 实现难度 I

- I0 精确执行：文件/符号、允许改动、步骤与验证已明确，几乎没有设计选择。
- I1 常规实现：契约已冻结；主要行为路径和责任模块已找到；实现由既有模式直接导出；测试主要验证本模块或简单集成。跨多个文件本身不升级。
- I2 复杂但边界已冻结：至少一个复杂性事实成立：正确性依赖两个以上模块/运行层之间的交互不变量；多个失败/重试/恢复分支相互作用；根因需要验证多条竞争性调用路径的因果关系；或即使契约明确，仍无法从现有实现和测试直接导出可执行修改步骤。必须记录具体模块、分支或待验证因果链，不用“任务很复杂”作理由。
- I3 极少数高后果的封闭问题：I2 档经带新证据的尝试仍无法解决，且范围和契约没有变化。进入人工复核后才考虑最高档。

### 5.3 审计风险 A

- A0 常规：局部行为与相关回归验证；不改变高后果公共边界。
- A1 深度：跨模块不变量、错误/恢复路径、严格变量/符号限制、来源等价或复杂负面约束审查。
- A2 关键：安全、权限、计费、持久化、公开契约、密钥/隐私边界或项目文档标出的高后果门禁。

实现低档不代表审计可以降档。风险按被影响的契约和后果确定。

## 6. 路由矩阵

| 对象 | 档位 | 模型/推理强度 | 适用条件 |
| --- | --- | --- | --- |
| 主控 | 推荐常规配置 | gpt-6-luna / high | 由用户在会话设置；Skill 不声称自动改主会话配置 |
| 思考 Agent | 唯一默认 | gpt-6-sol / xhigh | D1；只产出解决歧义所需的短结论 |
| 执行 Agent | I0 | gpt-6-luna / low | I0 全部条件有原文/证据支持；不得自行补设计 |
| 执行 Agent | I1 | gpt-6-luna / high | V2 常规执行档 |
| 执行 Agent | I2 | gpt-6-luna / xhigh | 契约明确但调试或实施复杂 |
| 执行 Agent | I3 备用 | gpt-6-luna / max | 高后果封闭问题；需问题编号、新证据及升级理由，不作常规档 |
| 审计 Agent | A0 | gpt-6-luna / high | 默认独立审计档 |
| 审计 Agent | A1 | gpt-6-luna / xhigh | 深度跨模块或严格负面约束审查 |
| 审计 Agent | A2 | gpt-6-luna / max | 高后果、需严格证明的最终门禁 |

除表中思考职责外不常规使用 Sol。任何模型/强度如未在当前 Codex 环境中确认可用，应标记为未验证或不可用，不能静默替换并声称满足。复杂度升级必须有具体触发条件；普通失败、任务体量、审计员偏好都不够。解决问题或范围缩小后回到较低档，记录变化即可。

边界判例：一次性对多个模块做完全相同、已有映射和测试覆盖的机械改名，不因文件数进入 I2；若行为跨服务状态转换且回滚/重试顺序会改变结果，则属于 I2。只验证一个字段的局部无副作用差异通常是 A0；验证跨模块幂等、权限或扣费语义属于 A1/A2，取决于项目后果分类。规模、文件数和改动行数不能单独决定档位。

### 6.1 I0 低档准入

只有同时满足以下条件，才可用 Luna low：

1. 任务目标、非目标和修改方法无歧义。
2. 允许修改的文件/符号或变更类型明确。
3. 不改变公开 API、Schema、状态、事件、安全、权限、持久化或外部副作用。
4. 来源实现已经定位；若任务要求复用原代码，已有来源证据。
5. 成功与失败检查方式已确定，执行者无需发明变量、接口、回退或验收口径。

任一条件不满足则使用 I1 或先处理 D1。low 不是防止跑偏的机制；冻结契约、唯一写入边界和持续审计才是。

## 7. Hook 与配置分层

### 7.1 固定角色配置

路由表是 Skill 的稳定决策依据。Codex 自定义 Agent TOML 是可选执行载体；每个 profile 固定 name、职责、developer instructions、model、model_reasoning_effort 和适当的只读/可写 sandbox。思考与审计 profile 默认只读。

自定义 Agent 配置可能覆盖显式 spawn 参数，且不同工具面未必允许按名称启动自定义 Agent。因此必须确认 profile 是否被当前入口加载，并以运行时元数据验证实际模型和强度。Agent 配置文件存在不能证明该次派发使用了它。

### 7.2 Hook 作用

仅在当前派发入口通过运行时探针时，PreToolUse 负责：

- 检查 V2 route marker、职责/阶段/profile 对应关系和允许的 fork 上下文。
- 对同一职责内可安全校正的 model/reasoning 参数做最小改写，并返回短小脱敏收据。
- 对角色、阶段、契约修订、未知 profile 或不受控继承等语义/结构错误直接拒绝。
- 对不带 V2 标记的普通其他工具保持透明，不改变其他 Skill 行为。

Hook 不扫描任意 shell 文本，不判断功能需求是否合理，也不以输出收据证明模型实际生效。可结构化匹配的文件范围门禁可作为单独可选检查；不能机器可靠判定的范围与行为仍由差异审计及项目 CI 负责。

官方 Hooks 文档的 Tool coverage 与 PreToolUse 章节说明：多数本地函数工具将 tool_name/tool_input 交给 PreToolUse；支持的返回形式包括 permissionDecision=deny，以及 permissionDecision=allow 配合 updatedInput。专用派发入口是否经过该路径仍须实测；官方明确部分专用工具路径可以退出默认 Hook 路径。SubagentStart 可提供上下文，却不能阻止子 Agent 启动。见 [Codex Hooks](https://learn.chatgpt.com/docs/hooks)，核对日期为 2026-09-26。文档未给出适用于所有 Codex 工具版本的固定 schema 版本号；实施时须记录该版本文档中的字段形状、Codex 版本和实际 Hook 输入/输出，不得自行宣称稳定 schema。

## 8. Hook 不可用时的降级

Hook 状态与运行路由是两个独立字段，不互相代替。

Hook 状态：

- HOOK_ENFORCED：新鲜会话证明该入口可纠正合法输入、拒绝非法输入，并对普通工具保持预期透传。
- HOOK_UNAVAILABLE：入口未触发 Hook、Hook 不受信任/未加载，或改写/拒绝探针失败。
- HOOK_UNVERIFIED：尚未完成探针或证据不充分。

运行路由状态：

- PROFILE_VERIFIED：子 Agent 通过指定自定义 profile 启动，实际模型与 effort 有可核对运行元数据。
- EXPLICIT_ROUTE_VERIFIED：子 Agent 通过显式 model/effort 启动，实际模型与 effort 有可核对运行元数据。
- ROUTE_UNVERIFIED：没有可核对的实际运行元数据，无法判断实际模型/effort 是否符合预期。
- ROUTE_MISMATCH：存在可核对的实际运行元数据，且实际模型或 effort 与期望不符；这是已证实的路由失败，不是缺少证据。

运行 provenance 的读取来源不得预设。实施 Phase 0 必须建立 Provenance Source Register，记录目标 Codex 版本、派发工具、实际可用的读取接口/界面、字段名、样例证据及其稳定性。候选位置可包括 Codex 子会话运行元数据或桌面 UI 中的会话详情；必须实测并只记录确有的字段，不能假定 read_thread、工具返回值或 transcript 会提供它。若找不到同时证明 model 和 reasoning effort 的来源，路由维度为 ROUTE_UNVERIFIED。

HOOK_ENFORCED 可以与 PROFILE_VERIFIED、EXPLICIT_ROUTE_VERIFIED、ROUTE_UNVERIFIED 或 ROUTE_MISMATCH 同时存在。前者只证明 Hook 对本次可观察输入执行纠错/拒绝；只有实际运行元数据证明模型路由是否符合预期。Hook 可继续提供纠错价值，但不能补齐缺失的 provenance，也不能掩盖已证实的路由不匹配。

按当前证据选择派发方式：优先使用已验证 profile；其不可调用时使用已验证显式路由。Hook 是否能附加纠错层单独记录。若实际值与目标不符，标记 ROUTE_MISMATCH；不得把它改记为未验证，也不得在硬路由约束下继续把该子 Agent 的工作当作合格证据。可在授权范围内改用另一条已验证路径并重新派发；若无可用路径，则只继续不依赖未知子 Agent 的主控定界、文档准备和安全单会话工作。若用户将指定模型/强度列为硬要求，或任务必须由该路由的独立 Agent 完成，相关验收项保持未通过并说明最小缺口。

Hook 故障不会自动把 Luna 改成 Sol，也不会静默选择更高强度。只将 Hook 状态记为 HOOK_UNAVAILABLE 或 HOOK_UNVERIFIED，并选择下一条已验证运行路由；如果没有已验证路由，就标记 ROUTE_UNVERIFIED。若实际运行值已被证明不符，则保持 ROUTE_MISMATCH，不能降格为 ROUTE_UNVERIFIED。

## 9. 任务记录与状态

复用项目已有记录；没有时使用一份简短任务记录，至少含：

- 用户目标原文、非目标、依据路径和硬约束 ID。
- 起始提交/工作区差异及来源仓库固定版本（任务要求时）。
- 允许改动、唯一写入者、当前阶段与交接状态。
- D/I/A 判定、目标 profile、升级触发和可验证的模型路由状态。
- 契约版本、任务版本、验收条件、测试结果与证据局限。
- 审计责任人、结论、拒收问题、修正/补证负责人及复审版本。

最小状态流：定界和基线 → 处理必要歧义 → 冻结契约 → 执行 → 固定版本 → 独立审计 → 通过 / 修正 / 补证 / 契约回流 / 等待必要决定。

## 10. 决策记录

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 是否每项任务都派难度 Agent | 否；主控用 D/I/A 简表分类，实质歧义才调用思考 Agent | 多一次判断会增加 Token 和等待，且不自动提升分类可靠度 |
| Hook 是否为核心依赖 | 否；Hook 是可验证的纠错/拦截层，固定 profile/显式参数是降级主线 | 专用派发路径可能绕过 Hook，单一路径造成不必要阻塞 |
| Hook receipt 的含义 | 只证明 Hook 处理过输入，不能单独证明实际模型 | 输入修正与子会话有效配置是两个事实 |
| 低强度是否用于全部执行 | 否；只给严格 I0 精确执行，常规执行仍为 Luna high | low 适合低选择空间工作，不是抑制跑偏的普遍手段 |
| 如何证明质量 | 独立差异/符号/行为审计、回归测试和固定版本证据 | 模型更强或多个 Agent 意见一致均不能替代证据 |

## 11. 平台事实与限制

官方 Subagents 文档的 Model choice、Custom agents 和 Custom agent file schema 章节支持自定义 Agent 配置及 model/model_reasoning_effort 字段，并说明配置继承与优先级；实际优先级和运行信息需要在目标入口验证。见 [Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)，核对日期为 2026-09-26。

本机现有 V1 记录过当前 collaboration.spawn_agent 路径未通过 Hook 改写/拒绝探针。V2 不把旧结论当成所有新版本的永久事实：保留为回归案例，在实施阶段重新验证当前版本。
