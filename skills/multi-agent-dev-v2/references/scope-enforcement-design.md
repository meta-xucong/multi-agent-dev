# Scope enforcement design

## Objective

Make the user's existing Scope discipline effective in delegated work: every worker and auditor receives all eight rules, the monitor reports a concrete violation immediately, Main addresses it before continuing the affected work, and the monitor checks the correction. Keep the five-minute review as a best-effort supplement, not the sole checkpoint. The monitor remains read-only with respect to the project.

## Agent workflow

Every dispatch includes the original request, subsequent scope changes, relevant project instructions and the complete Scope discipline from `SKILL.md`. Code and design auditors check additions and the actual call path against the rules as well as requested behavior. They cannot turn a hypothetical or non-P0 edge case into a required fix. A final scope review checks the actual final changes, including calls into existing hash-generating code, not just the names of changed files.

On the first concrete violation, the monitor immediately messages Main, then returns a single machine-readable finding as its first output line. Main actively collects and handles monitor findings before writing, adopting an audit fix, running tests, or delivering. At the next available coordination point it stops the affected writer, verifies the current evidence, corrects only the violation, requests a focused monitor recheck, and resumes after confirmation. If new user instructions or evidence disprove the finding, the monitor can resolve that same issue without inventing a code change. No audit `PASS` or task completion is allowed while a confirmed violation is unresolved. A proposal lacking P0 evidence or a verified fallback consumer is not authorization to implement it.

## Optional synchronous Hook

The hook is a separately configured, trusted and runtime-verified enhancement; an installed skill alone does not activate it. Codex documents that non-managed Hook trust is bound to a hash of the definition: https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks . This conflicts with the user's no-hash rule. Do not run that trust path, or a live probe whose required operations generate or verify a hash, without explicit authorization for those hash operations. Merely requesting the Hook does not authorize them. If the runtime's behavior cannot be established without executing a potentially hash-generating path, leave activation unverified and use message-based monitoring. The handler's own state operations use no hashes; this does not establish the behavior of the surrounding platform.

On the monitor's initial registration turn, its first output line is `MADV2_SCOPE_V1` plus a JSON `REGISTER` record. `SubagentStop` records the actual event's `agent_id` under its root `session_id` and emits an observable registration receipt. Main must match that receipt to the monitor it actually dispatched; the agent's text alone does not prove the Hook ran or identified the right agent. Later first-line `VIOLATION`, `ALLOW` and `RESOLVED` records are accepted only from that bound agent and session. If registration or session binding cannot be observed in the target runtime, enforcement is unverified. A different agent's ordinary registration cannot replace an existing binding. While issues are pending, the current monitor must first authorize the exact replacement agent ID via `TRANSFER`; the replacement then registers with `replace=true`, preserving pending issues. If the current monitor cannot authorize transfer, report the unresolved blocker. State is local control metadata outside the project and uses no hashes.

For pending issues, `PreToolUse` rejects supported `apply_patch` calls touching their affected paths; unrelated patches may proceed. If an issue concerns an action with no specific path, all patches are paused. Since the effect of an arbitrary shell command cannot be inferred reliably, `Bash` calls in that session are paused while an issue is pending. Main can ask the registered monitor to approve an exact read-only or corrective command or patch; its `ALLOW` record contains all current issue IDs, tool name, working directory and complete exact tool input. Only that exact one call may pass. Main may send the read result to the monitor or resume it to execute the approved read itself. The monitor remains read-only for project files; corrective changes are made by Main or the assigned writer. Pending issues do not cause policy denial in other sessions. A globally configured Hook still runs for matching events in other sessions and adds process and state-access overhead. New violations are retained alongside existing ones, never overwrite them, and revoke any previously approved action.

Each issue remains pending until the monitor rechecks the correction or a disproved finding and returns `RESOLVED` with the same ID. The Hook emits a receipt for each accepted state change; Main must observe it before relying on that change, and treat a missing receipt as unverified while still following the monitor's message. A distinct finding that repeats an existing ID is retained under a new ID announced in a Hook receipt. On `Stop`, a pending issue requests one continuation. If `stop_hook_active` is already true or the monitor/correction is unavailable, stop that continuation with an unresolved reason; retain pending state and report the blocker instead of looping or claiming completion.

The Hook does not infer semantic P0/consumer evidence from text. While a finding is pending, the conservative Bash pause also delays unrelated shell commands until the monitor approves them; unaffected `apply_patch` calls and independent sessions can continue. Other write-capable tools, already-running calls, unsupported paths, Hook failures, untrusted/unloaded hooks and asynchronous work are outside its verified boundary. Do not claim system-wide prevention or automatic five-minute timing. Do not install or trust hooks globally as part of using the skill.

The bundled handler is `hooks/scope_guard.py`; `hooks/scope_guard.hooks.json.example` shows the event wiring. It is not registered by the skill. For every monitor result below, put exactly one JSON object on the first line after `MADV2_SCOPE_V1 `; issue IDs are local labels, not hashes. `paths` must contain absolute paths, including a drive or UNC share on Windows; it can be empty for a pending action that cannot be tied to a file. If a report contains a non-absolute path, the Hook reports that it did not register the issue and asks the monitor once to correct the report; Main must handle the finding and cannot claim enforcement until a valid receipt arrives. If a patch event has no `cwd`, path coverage is unverified and the Hook reports that limitation.

```text
MADV2_SCOPE_V1 {"status":"REGISTER"}
MADV2_SCOPE_V1 {"status":"VIOLATION","issue_id":"issue-1","rule":"no SHA","evidence":"new call invokes SHA-256","paths":["C:\\work\\src\\example.py"]}
MADV2_SCOPE_V1 {"status":"ALLOW","issue_ids":["issue-1"],"tool":"Bash","cwd":"/project","tool_input":{"command":"cat src/example.py"}}
MADV2_SCOPE_V1 {"status":"RESOLVED","issue_id":"issue-1"}
```

`ALLOW` uses the exact `tool_name`, `cwd`, and complete `tool_input` that the Hook will receive; it is consumed by one matching call and does not resolve an issue. For an `apply_patch` correction, place the exact patch in `tool_input.command`. A new finding revokes a prior approval. To replace a monitor while an issue is pending, it first returns `{"status":"TRANSFER","agent_id":"replacement-id"}`; that agent then registers with `{"status":"REGISTER","replace":true}` and Main checks the actual Hook receipt against its dispatch. The default state database is under the user's `.codex/state/multi-agent-dev-v2/`; `MADV2_SCOPE_GUARD_DB` selects an isolated database for local tests.

## Validation

Exercise the protocol in isolated temporary state: registration binds the actual monitor ID; violation blocks affected patches and Bash, unrelated patch paths and sessions remain usable; monitor-approved exact reads and corrections pass once; multiple findings and monitor replacement do not lose pending issues; an issue stays pending until matching recheck; and unresolved Stop requests at most one continuation. Confirm unrelated agents do not alter an issue. Independently review that every role receives the hard rules and that no new hash generation, speculative edge handling or extra fallback was introduced. A synthetic Hook test proves only the handler logic; live Codex Hook registration, trust, event coverage and parent/subagent session binding require a separate actual runtime probe before claiming enforcement.

An isolated Windows CLI probe with a temporary user configuration and one-time Hook trust bypass observed registration and violation receipts for the same parent session and monitor agent, denial of the affected `apply_patch`, and no Hook denial after `RESOLVED`. The subsequent patch was rejected by the test environment's read-only sandbox, so successful downstream writing after resolution was not verified. This probe does not configure or verify the desktop application's active Hook or other tool paths. That particular run was performed under a specific user authorization for hash operations. This historical authorization is not permission for future sessions, other users, or unrelated tasks.

A subsequent Windows CLI probe used the user's globally configured, persistently trusted Hook without a trust bypass and an isolated state database and test file. The affected patch was denied while the finding was pending; after the same monitor resolved it, the next patch completed and the test file contained the expected new content. This confirms that CLI configuration and call sequence, not Hook activation in an already running desktop session or coverage of every write tool.
