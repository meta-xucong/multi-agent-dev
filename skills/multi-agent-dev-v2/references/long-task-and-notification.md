# Long tasks and terminal notifications

## Conditional context-lean

Use `context-lean` only for long/multi-phase work, large reads, repeated handoffs, approaching context limits, or observable context degradation. Short clear tasks stay `NOT_NEEDED`; do not load a second skill for appearance. When a trigger occurs, load/route to the `context-lean` skill automatically if the platform supports linked skill activation; do not ask the user to invoke it a second time. If this Codex surface cannot load a linked skill, apply only the minimal checkpoint/recovery rules here and say the companion was not actually loaded. When activated, preserve the frozen contract, baseline, exact current writer, open issues, diff/version and next action in each checkpoint. After compaction/recovery, re-check those facts before writing. Context management cannot change scope, route, writer, audit, or authority.

## ServerChan terminal notification

At the end of every task send exactly one ServerChan notification for `done`, `blocked`, or `stopped` via `../scripts/notify_serverchan.py`. Use the same SendKey lookup contract as V1: `SCT_SENDKEY`, then `%USERPROFILE%\.codex\secrets\serverchan_sendkey.txt`; never put the secret in code, arguments, output, or evidence. `done` requires a concrete verification result. `--task-id` is optional; if supplied, it is a local-only idempotency key and must not appear in the ServerChan body or plaintext receipt. Omitting it supports direct notification for tasks without a routed agent. Report notification delivery success or failure honestly. Do not append a hidden or visible machine-readable terminal marker to the final Codex response.

The V2 notifier uses an isolated task receipt namespace at `%USERPROFILE%\.codex\state\multi-agent-dev-v2\`; it never reads or deletes V1 state. Dry-run and unit tests use temporary state and mocked HTTP, never a real SendKey or network request.

V2 includes an optional lifecycle handler at `../hooks/task_terminal_notify.py`. If manually configured and verified, the main session requests active-session registration at task start by directly invoking the absolute path to this package's `scripts/notify_serverchan.py` with `--register-active --task-id <safe-id>`; the `PreToolUse` handler matches Codex's canonical `Bash` tool name and reads `tool_input.command`, then associates only a hash of that ID with the current session. Registration rejects wrappers, shell composition, a different script path, and extra notifier arguments. Its transparent pass-through emits no stdout because `PreToolUse` does not support the shared `continue` field. A normal terminal send writes a local pending intent before networking. `Stop` retries only a pending intent (ordinary assistant turn stops do not notify); `Interrupt`/`SessionEnd` retries a pending intent or sends a generic `stopped` fallback for an active task. The sample config caps both lifecycle handlers at Codex's documented three-second maximum and uses bounded notifier retries. Successful direct delivery receipt prevents duplicate compensation. No machine-readable terminal marker is used.

The handler is not automatically installed or trusted. Its PreToolUse command shape, event inputs, and Stop/Interrupt/SessionEnd activation must be probed in the target Codex version. Until those probes pass, report `HOOK_UNVERIFIED`; a successful `--register-active` CLI response only means the request was made, not that the Hook recorded it. The explicit terminal notifier remains the supported path without Hooks, but interruption compensation is unavailable in that mode. A notification failure is a delivery risk and must be surfaced; do not claim it was sent.
