# 上下文压缩规则优化（context-lean）

> 基座：rohitg00/pro-workflow 的 `context-engineering` + `context-optimizer` + `compact-guard` 三份 skill 的压缩相关部分，适配 WorkBuddy + aiself.vip 中转站场景。已剔除与压缩无关的内容。

## 问题定义（WorkBuddy + aiself.vip 实测）

WorkBuddy 在上下文达到模型上限的 **90%** 时自动触发紧急压缩（`shouldCompact`，日志可查）。压缩的三笔代价，全部来自 2026-09-07 实测：

1. 摘要请求本身耗时：大上下文经中转站实测 **208 秒**（3.5 分钟），期间 UI 无输出
2. 压缩重写全部历史 → 上游 prompt cache 全灭 → 之后每轮请求全量 prefill，~9 万 token 实测 **TTFT 19.4 秒**
3. 子代理的思考/工具调用**不渲染**到主会话 UI，压缩时用户感知为「卡死」

更深一层（来自 context-optimizer）：**超过 90% 就进入「dumb zone」**——模型注意力被海量 token 稀释，压缩质量、判断力都已下降。所以压缩优化有三层目标：**能晚压就晚压 → 非压不可就主动压（别等被动）→ 压之前存状态、压之后能恢复**。

## 第一层：推迟压缩（减少触发次数）

核心：控制上下文膨胀速度，让 90% 来得更晚。

| 手段 | 怎么做 | 节省幅度 |
|---|---|---|
| 大输出落盘 | 命令输出/文件内容/数据样本 >150 行写入文件，对话只留路径+摘要 | 最大头 |
| 精准读文件 | Glob→Grep→Read(offset/limit)，禁止无参全读 >500 行文件 | 每次读省 50~90% |
| 探索交给子代理 | 大范围搜索/批量处理派 Agent 子代理，主上下文只收结论 | 每次搜索省 30~60% |
| 工具输出瘦身 | 长命令加 `| head -50`/`tail -50`；日志读头20+尾20 | 视输出量 |
| 最小 diff 编辑 | 用 Edit 不用 Write 整文件重写 | 每次编辑省全文 |
| 提示收敛 | 给 agent 的指令带具体路径和约束，不给「帮我修一下」这种模糊提示 | 避免全盘扫描 |

## 第二层：主动压缩（别等 90% 被动压）

WorkBuddy 有 `/compact` 命令。**主动压缩远好于被动压缩**：被动触发时模型已在 dumb zone，压缩质量最差；主动压可以在状态还好时做，还能带 focus 指定保留重点。

**主动压缩时机：**

| 时机 | 动作 |
|---|---|
| 规划完成、进入实现前 | `/compact 保留：需求要点、接口定义、已确定的方案` |
| 完成一个功能/里程碑后 | `/compact 保留：XX 模块的改动、关键决策` |
| 切换任务域之前 | `/compact 保留：前一个域的结论` |
| 大读取/大搜索完成后 | 先提炼要点写入 PROGRESS.md，再 `/compact` |
| 出现退化信号（重复/遗忘/引用错文件名） | 立即 `/compact`，不要等到 90% |

**被动压缩的兜底**：即使没主动压，90% 时系统也会自动压——但那是下策，208 秒 + cache 全灭的代价照付。

## 第三层：压缩前存状态 + 压缩后恢复（compact-guard 核心）

**永远不要在无状态保存的情况下压缩。**

### 压缩前清单（存到 PROGRESS.md）

压缩前必须落盘以下 5 项。WorkBuddy 的压缩恢复文件数量和单文件 token 上限目前没有公开确认，不能套用 Claude Code 的内部常量；因此把状态集中写入一个小型 `PROGRESS.md`，并通过 WorkBuddy 的 `PreCompact` / `SessionStart(source=compact)` 事件做保存与恢复：

1. **当前任务**：正在做什么，一句话
2. **进行中的文件**：正在编辑哪些文件（不超过 5 个）
3. **已做决策**：本次会话的架构/技术选型及理由
4. **阻塞项**：当前卡在哪
5. **下一步**：压缩后要立即执行的动作

### 压缩前后自动化（WorkBuddy 已确认的事件）

WorkBuddy Hooks 文档确认支持：

- `PreCompact`：压缩前触发，`matcher` 可区分 `manual` / `auto`；适合把当前任务、进行中文件、决策、阻塞、下一步写入 `PROGRESS.md`
- `SessionStart`：压缩后可用 `matcher: "compact"` 触发；适合读取 `PROGRESS.md`，通过 hook stdout 作为额外上下文注入
- `PostCompact`：文档总览列出，但当前文档没有给出 matcher、输入或输出细节；暂不依赖它

最小配置形态（示意，先在项目级验证，不直接写入全局 settings）：

```json
{
  "hooks": {
    "PreCompact": [
      {
        "matcher": "manual|auto",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$CODEBUDDY_PROJECT_DIR/.workbuddy/hooks/before-compact.py\"",
            "timeout": 60
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "matcher": "compact",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$CODEBUDDY_PROJECT_DIR/.workbuddy/hooks/after-compact.py\"",
            "timeout": 60
          }
        ]
      }
    ]
  }
}
```

Hook 脚本必须满足：失败时不删除已有 `PROGRESS.md`；保存动作采用临时文件写入后替换；恢复脚本只输出短摘要，不把完整日志重新注入上下文。

### 压缩后恢复 4 步

1. `SessionStart(matcher=compact)` 自动输出 `PROGRESS.md` 的短摘要
2. 重读最优先的文件（正在编辑的那个）
3. 查看 `PROGRESS.md` 确认任务进度
4. 从「下一步」继续；若 hook 未触发，再手动执行以上 2~4 步

## 辅助：token 效率（减少每一轮的消耗）

来自 token-efficiency / context-optimizer，与压缩间接相关（消耗慢 = 膨胀慢 = 压缩来得晚）：

- **不重复读**：文件没改过就不要再读一遍
- **改前必读**：没读过的文件不要改
- **tool-call 预算**：快速修复 ≤20 次工具调用，大功能 ≤80 次
- **同一失败最多重试两次**：第三次还失败就停下来换思路，不要硬磨
- **输出结构化**：表格/列表优于大段文字，无阿谀开场白和结尾废话

## 何时 /clear vs /compact vs 派子代理

WorkBuddy 有 `/clear`（清空）和 `/compact`（压缩）两个内置命令：

| 情况 | 动作 |
|---|---|
| 任务边界，想保留经验结论 | `/compact 保留：关键结论` |
| 上下文已退化（重复/遗忘/引用错） | `/compact`，若仍不行则状态固化后开新会话 |
| 开始完全不相关的工作 | `/clear` 或新会话 |
| 重度读/搜索操作 | 派子代理 |

## 反模式清单

- ❌ 只需要一个函数却整读整个文件
- ❌ 大段工具输出用完之后还留在上下文里反复引用
- ❌ 攒到 90% 被动压缩，而不是在任务边界主动 `/compact`
- ❌ 无状态保存就压缩（压缩前没落盘 5 项清单）
- ❌ 压缩后凭记忆继续，不重读 PROGRESS.md
- ❌ 给子代理发「帮我全面研究一下 X」这种无边界指令
- ❌ 同一失败重试超过两次还不换思路

## 边界

- 落盘不等于做完，验收标准不变。
- 瘦身砍的是「重复和大段原文」，不是「关键信息」——错误信息、路径、回滚步骤必须保留。
- 用户明确要求全文输出/贴出时，照做，用户偏好优先。
