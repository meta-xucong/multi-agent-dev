# 自适应四职责工作流开发文档

> CONTRACT_REV: v1.3.1-route-guard。本文是 `multi-agent-dev` 的执行参考，不覆盖用户最新要求、项目 `AGENTS.md`、开发文档、章节门禁、权限边界或外部系统授权；发生冲突时以上规则优先。本文不创建常驻 Agent、不中途改变自动调用策略，也不能授权提交、推送、部署或付费调用。模型路由硬门禁、`MAD_ROUTE_V1` marker、Hook I/O 和测试矩阵以 [docs/model-routing-hard-gate-development.md](../docs/model-routing-hard-gate-development.md) 为准。

## 1. 目标与不变量

本工作流用一份任务记录串联四种逻辑职责，在有意义的决策或证据出现时交接，尽量不复制上下文。它保留以下硬门禁：

- 用户规则和项目规则优先；先冻结用户目标、非目标、范围、基线和唯一写入负责人。
- 优先复用已有实现、接口、变量、测试和项目门禁；不凭“更好”扩大需求、另造平行逻辑、兼容路径、验收标准或依赖。
- 每次只做最小必要改动，保留稳定的送审版本；起始未提交改动属于基线，不覆盖、不冒充本次成果。
- 独立审计只对固定版本给出“符合 / 不符合 / 证据不足”；审计员不修改被审代码、测试或验收标准，也不自动修复或补证后自批。
- 逐项保存可观察证据；拒收后按“修正或补证 → 固定新版本 → 重跑受影响检查 → 独立复审”回流。无新证据的机械重试停止。
- 缺少依据、权限或外部条件时，说明证据、已尝试方法和具体缺口；不擅造基线、不降验收标准。未完成目标不能因安全拒绝、禁用或等待而标记完成。

## 2. 四种逻辑职责

四种职责是工作边界，不是四个 Agent 常驻。主控通常是当前会话，不能再派生一个主控；子 Agent 不得递归扩编。

| 职责 | 启用条件与产出 | 明确边界 |
| --- | --- | --- |
| 主控 | 读取依据，建立任务记录，决定当前状态、下一负责人和是否升级，集成并交付 | 不自行扩大范围、不豁免约束、不用多数意见代替证据 |
| 按需思考 | 只有需求、架构、契约或验收有实质歧义时启用；只读输出可执行决策、选项、风险和未决问题 | 不写代码、不改测试、不替用户扩范围、不要求或保存隐藏推理；清晰小任务跳过 |
| 执行 | 在冻结执行契约和唯一写入边界内改代码、定向测试并报告差异；允许实现层局部推理 | 不改变公开 API/schema/状态/事件/安全/权限/持久化/外部副作用语义，不增加需求、平行逻辑、兼容路径或改验收标准 |
| 独立审计 | 在版本冻结后读取原文、差异、测试和证据，复核功能、边界、范围及过度开发 | 不修改被审对象，不要求或声称看到隐藏推理；审计结论不是执行者自证 |

小任务可以由主控兼任执行，再安排独立审计；有真实独立产出时才派执行 Agent。只读调查是一次性任务，不会形成第五种常驻职责，也不自动获得修复权限。

## 3. 一份任务记录与冻结执行契约

优先复用项目现有任务单、章节记录或审计记录，不建立重复台账。最少保留用户要求原文及以下字段：

```text
任务 ID / 需求 ID：稳定标识
目标与非目标：这次要交付什么，明确不做什么
依据与硬约束：原文路径/章节、C1…约束、检查方法
基线与契约修订：起始提交、已有未提交改动、CONTRACT_REV
门禁与交接：COMPLEXITY_GATE、当前唯一写入者、WRITER_STATUS、AUDIT_OWNER、停止/交接证据
分工与写入边界：主控、思考（如有）、执行、审计、允许文件/模块
公共不变量：API、schema、状态、事件、安全、权限、持久化及外部副作用语义
验收与证据：R1…条件、命令/复现、预期、实测、退出码和覆盖局限
版本与开放问题：送审版本/补丁或哈希、问题编号、证据、责任人、下一状态
```

执行契约冻结后，执行者每次编辑前逐项核对目标、非目标、允许文件、唯一写入者、不变量和验收。只传交接所需的稳定 ID、契约修订、版本、需求 ID、证据、开放问题和下一负责人；不复制全会话或全日志。契约修订或代码变化后，旧证据按影响范围失效，必须重新固定版本并复核受影响项。

执行者可以在实现层局部推理，但不得把局部判断变成公共语义。发现需要越过契约时，停止依赖该决定的路径，提交：

```text
DESIGN_QUESTION：触发位置与实际差异
现行契约：对应字段、状态、事件、安全或权限不变量
影响：若继续实现会改变什么，影响哪些文件/测试/外部副作用
最小决定：需要主控确认的一个选项或缺失依据
不受影响的工作：可以安全继续的独立路径
```

`DESIGN_QUESTION` 只暂停依赖路径；需要扩范围、改公共契约、放宽限制或取得权限时，进入契约回流或等待用户，而不是在执行层默许。

### 3.1 写入者交接安全门

更换唯一写入者不是普通调度动作，而是硬门禁。主控必须先调用平台支持的停止/中断操作，再查询状态；只有确认旧写入者为 `inactive`、`completed` 或 `failed`，且没有进行中的写入操作，才可在任务记录写入 `WRITER_STATUS` 和停止证据后派发替代者。停止调用失败、状态未知、旧 Agent 仍活动或工作区状态无法确认时，禁止启动替代写入者；只能等待、补查或请求用户决定。额度耗尽、工具错误、口头声明或“看起来没有继续输出”都不是停止证据。替代者必须收到上一版本、已改文件、未解决问题和验证结果，且重新确认唯一写入边界。

## 4. 事件驱动四步流程

这里的“事件”是交接、决策、差异、审计结论或阻断条件等可观察工作结果，不是软件事件总线，也不是定时轮询。主控在事件发生后选择下一状态和责任人。

```text
定界/基线 →（必要时思考）→ 契约冻结 → 执行 → 版本冻结 → 审计
                                                     ├→ 通过
                                                     ├→ 实现返工
                                                     ├→ 补证
                                                     ├→ 契约回流
                                                     └→ 等待用户
```

### 4.1 主回合停滞与关闭收敛

主任务回合和子 Agent 状态必须分开观察。一次有界等待后，若主回合仍为 `active/inProgress`，没有新的助手消息、工具事件、最新工具标记或错误，而子 Agent 均为 `inactive/completed/failed`，或为 `idle/notLoaded` 且读取成功、其回合没有 `inProgress` 和进行中写入，登记 `ORCH_STALE_SUSPECTED`；任何读取失败、空结果或状态无法证明都进入 `ORCH_BLOCKED_NEEDS_USER`。若 `wait_threads`、`read_thread`、UI 或其他来源对同一回合给出矛盾状态，登记 `ORCH_STATE_CONFLICT`，只允许一次无写入复核，不得无限等待、重复 `closeAgent`、fork 或据“没有输出”认定主回合已停止。完整恢复矩阵见 [docs/stalled-orchestration-recovery-development.md](../docs/stalled-orchestration-recovery-development.md)。

`closeAgent` 失败必须先读取同一 `receiverThreadId`：`inactive/completed/failed` 且无进行中写入表示重复/旧句柄关闭失败，停止重试；`idle/notLoaded` 只是 UI/加载状态，必须额外确认没有 `inProgress` 回合和进行中写入；仍活动才允许一次停止/取消后复核；状态未知则阻断替代写入者。只有一次停止/取消调用或“停止并收敛”用户输入被平台接受/排队后，才进入 `ORCH_STOP_REQUESTED`；调用不支持、失败或未被接受则直接进入 `ORCH_BLOCKED_NEEDS_USER`。已排队但尚未中断的请求只保持 `ORCH_STOP_REQUESTED` 到一次有界复核；复核仍无终止证据才转为 `ORCH_BLOCKED_NEEDS_USER`。只记录任务/回合 ID、快照、停止调用结果和 `WRITER_STATUS`，等待用户在界面停止或新建任务。主回合或旧写入者未确认终止前，不得 fork、接管或继续写入；恢复后必须重新固定基线、读取当前 Skill，并使用当前 `CONTRACT_REV`、合法 marker、非继承 fork 和 receipt。

### 4.2 监测模式与活动凭证

正式开发默认 `MONITOR_MODE=DELIVERY_SILENT`：不发送周期性心跳或重复无变化消息，只在交接、阻断、范围/契约变化和最终交付记录必要状态。只有用户明确要求监测或诊断运行中会话时才启用 `MONITOR_MODE=OBSERVE`，并按事件而不是固定间隔更新。

在 `OBSERVE` 模式，主控在建立基线、派发/收回子 Agent、开始或结束长操作、发现状态冲突和形成最终结论时发送一次 `STATUS_REPORT_V1`，只包含可观察元数据：

```text
task_id / turn_id / observed_at
phase / main_status / CONTRACT_REV
child_agents: id, role, status, last_event, expected_until, writer
active_writer / changed_files
last_progress_evidence / tests / audit_status
blockers / next_step / conclusion
```

长操作记录 `operation_started_at`、`expected_until`、`last_progress_at` 和负责人；预期窗口内没有消息不构成停滞。子 Agent 的活动必须有最近工具事件、文件变化、测试结果或 `STATUS_REPORT_V1`；UI 标签或口头声明不能单独证明活动。`wait_threads` 只作唤醒/粗状态，`read_thread` 事件/工具/文件记录作为活动证据，`list_threads` 只作导航参考；来源冲突进入 `ORCH_STATE_CONFLICT`。

`DELIVERY_SILENT` 下可将状态压缩写入现有任务记录或交接记录，不要求把报告反复发给用户；同一问题只有状态或证据变化时才更新。

### 第一步：定界与基线

1. 读取相关项目规则、开发文档、契约、既有实现和测试；只加载当前任务所需材料。
2. 检查工作区，记录起始提交、未提交及未跟踪改动；把它们作为基线，不覆盖或冒充本次差异。
3. 写入任务记录，明确目标、非目标、唯一写入者、允许改动、硬约束、依赖和验收方法。
4. 判断是否存在实质歧义。没有歧义则直接进入契约冻结；有歧义则只读派发按需思考。

### 第二步：按需思考与契约冻结

思考职责只处理需求、架构、契约和验收歧义，返回最小可执行决策；它不能写代码或替用户选择新增范围。主控吸收决定后冻结执行契约，包含允许/禁止改动、公共不变量、证据和版本标识。仍缺少用户选择、授权或关键依据时，进入等待用户，不让执行者猜测。

### 第三步：执行与持续纠偏

执行者按依赖顺序做最小实现和定向验证；每轮都比较范围、契约和实际差异。越界、依据缺失、违反约束或发现公共语义变化时，先停止扩散并提交 `DESIGN_QUESTION`。无关且已授权的安全工作可以继续；不能借“实现层推理”补造需求、协议、回退、阈值或验收。

### 第四步：版本冻结、审计与路由

执行者提交完整差异、基线、验证记录和已知问题后停止对送审对象写入。审计员独立读取原文和固定版本，必要时复跑正常、失败、边界和回归验证，再按证据结论路由：

- **符合**：主控集成并复验受影响用户流程；集成差异也要独立审计。
- **不符合**：主控自动组织并自动调度冻结契约范围内的修正，把具体问题和证据交回责任执行者；修正后固定新版本并重审，不由审计员直接修复。
- **证据不足**：主控自动调度授权范围内的补证，固定同一版本或新版本后由独立审计确认；审计员不能自行补证、口头补证或自动放宽标准。
- **契约回流**：问题必须改变范围、公共契约、硬约束或外部副作用语义时，更新依据并重新定界；旧证据按影响范围失效。
- **等待用户**：缺少授权、用户选择、基线或外部条件且安全替代验证不足时，只暂停受影响路径。

自动路由只表示主控把范围内的修正或补证交给责任人并推进固定版本、重跑检查和独立复审；它不允许审计员自修、自补证后自批。只要仍有安全且已授权的范围内步骤，一次拒收不要求用户再次说“继续”；只有扩大范围、改变契约、放宽硬约束或取得新权限时才等待用户。

任何版本在进入 `ACCEPTED` 前，必须同时满足：执行者已停止写入、版本已固定、必要测试已通过、所有必需证据已绑定该版本，并由 `AUDIT_OWNER` 完成独立审计。执行中、测试失败、版本未冻结或审计未完成时，状态只能是进行中、返工、补证或阻断，不得提交、推送或宣布完成。

### 4.3 任务结束通知

对实施任务，只有最终进入 `done`、`blocked` 或 `stopped` 才发送一次 ServerChan 微信通知；审计拒收后的范围内返工、普通测试失败、阶段交接和只读监测不发送。调用 `scripts/notify_serverchan.py`，沿用 `SCT_SENDKEY` → `%USERPROFILE%\.codex\secrets\serverchan_sendkey.txt` 的凭据顺序和默认 3 次重试。消息只保留项目、状态、摘要、关键验证和用户下一步；完整日志、隐藏推理和密钥不得发送。通知失败必须记录为交付风险并在最终回复披露；成功或明确记录交付阻断后才可报告终态交付。详细字段与示例见 [ServerChan 任务结束通知开发文档](../docs/serverchan-completion-notification.md)。

## 5. 模型与推理路由

模型策略是成本控制建议，不是 Skill 的权限系统；Skill 无法强制切换当前主会话模型。只有显式派发且平台支持时才设置子 Agent 的模型/推理强度；不可用时如实披露并使用可用配置，不得伪称。

### 5.1 保守升级门禁

契约冻结前，主控必须记录 `COMPLEXITY_GATE`，取值为 `SIMPLE_PROVEN` 或 `ESCALATE_REQUIRED`。只有同时满足以下条件，才允许执行者按 `gpt-5.6-luna/high` 启动：

- 仅涉及单一模块的局部改动；
- 用户目标、非目标和验收条件没有歧义；
- 不改变公共 API、schema、状态、事件、安全、权限、持久化或外部副作用语义；
- 没有跨模块依赖、共享边界冲突或 `DESIGN_QUESTION`；
- 现有实现、来源依据和验证方法足以直接落地。

任一条件不满足，或主控无法用任务记录中的原文和证据证明条件成立，就必须取 `ESCALATE_REQUIRED`，不得先用 `Luna High` 试做再补升级。路由规则为：设计/契约/语义问题只启用唯一的 `gpt-5.6-sol/max` 思考 Agent；契约已冻结但执行、调试、阶段门禁或审计复杂时，将主控/执行/审计从 `gpt-5.6-luna/high` 升为 `gpt-5.6-luna/max`。Sol 不用于执行或审计。主控必须记录触发条件、目标模型和推理强度；平台不支持目标配置时如实披露并使用可用配置，不得声称已升级。问题解决、边界收窄并重新证明为简单后，才可回到 `SIMPLE_PROVEN` 和默认强度。

| 职责 | 默认配置 | 允许升级的触发 |
| --- | --- | --- |
| 主控 | `gpt-5.6-luna/high` | 阶段门禁或异常裁决可用 `max` |
| 按需思考 | `gpt-5.6-sol/max`，只要启用就使用 `max` | 唯一允许使用 Sol 的职责；不常驻，不因任务大而启动 |
| 执行 | `gpt-5.6-luna/high` | 冻结范围内的复杂调试可用 `max` |
| 独立审计 | `gpt-5.6-luna/high` | 最终门禁或高风险可升为 `gpt-5.6-luna/max` |

`max` 不能因“更保险”、普通失败或任务较大自动启用。升级必须有稳定问题编号、触发证据和目标；问题解决或进入普通阶段后回到默认配置。自动切换当前主会话模型不在本 Skill 能力范围内。

### 5.2 `MAD_ROUTE_V1` 作用域化硬门禁

对 `Agent`、`spawn_agent`、`multi_agent_v1__spawn_agent` 的派发，用户级同步 `PreToolUse` Hook 只处理 `message` 第一非空行带 `MAD_ROUTE_V1` 的输入；没有 marker 的普通 spawn 必须 stdout 为空、退出 0，保持其他 Skill 透传，但以 `madv1_` 开头的 task_name 缺 marker 时 deny。标记调用必须带安全 `tool_use_id`，marker 的 `task_id` 和当前 `contract_rev` 也要通过精确校验。marker 合法性、角色/阶段配对和路由真值表见开发文档，合法输入的 `model`/`reasoning_effort` 必须由 `updatedInput` 覆盖到真值表值，并在 `hookSpecificOutput.additionalContext` 产生绑定 tool_use_id 的脱敏 `MAD_ROUTE_RECEIPT`；非法 marker、字段、阶段、gate、Agent 类型、task_name 或全历史 fork 必须在创建 Agent 前同步 deny。

每次派发必须显式携带目标 model、reasoning_effort 和适用平台的非继承 fork；Hook 的最小自动修正不是放宽要求。守卫兼容内置 `worker`、`explorer`、`default`，不扩展自定义 Agent 配置；当前 task_name 必须是与 marker 一致的合法 `madv1_<role>_<simple|escalate>_<slug>`，不能自动改名，缺失 fork_turns 可补 `none`，all/正整数/字符串正整数/其他值拒绝，旧式显式 `fork_context=true` 拒绝，fork_turns 与 fork_context 同时出现的混合 schema 直接拒绝。配置不使用全局 `[agents].default_subagent_*`；省略参数时 Luna High 主控继承只作兜底，复杂主控下遗漏不能放行。出现缺 marker/receipt、`xhigh` 或实际路由不符时，结果不得放行；receipt 不证明下游实际采用模型。错误 Agent 已启动时按停止、状态确认、记录 `WRITER_STATUS`、正确 marker 重新派发的失败回流执行。Hook 未重启或未通过 `/hooks` 信任时视为未启用并 fail-closed；不能自动切换已运行主会话模型。

## 6. 可观察审计与过度思考检查

审计不要求、推断或声称看到了隐藏推理；只检查能在版本和证据中复现的结果。至少逐项检查：

- 是否出现未授权的额外文件、抽象、字段、变量、方法、依赖、重命名或行为；
- 是否改变公开 API/schema、状态、事件、安全、权限、持久化、外部副作用或验收口径；
- 所有“严格变量/符号/方法约束”是否按原要求逐项比较声明、引用和行为，不能以总数不变、别名、动态属性、生成代码或测试排除偷换口径；
- 是否存在无新证据的重复尝试、全量日志搬运、轮询或不必要的模型升级；
- 正常、失败、边界、回归路径和版本哈希是否足以支持当前结论。

证据记录可采用：

| 要求 ID/原文位置 | 检查对象与方法 | 实际证据及局限 | 固定版本 | 结论 |
| --- | --- | --- | --- | --- |
| C1 / R1 | 文件、符号、差异、命令或复现 | 预期、实测、退出码、产物位置 | 提交/补丁/哈希 | 符合 / 不符合 / 证据不足 |

## 7. 失败归因、Token 控制与验收场景

先用基线对照、最小复现和现行契约归因：本次回归、既有缺陷、夹具/断言或契约错位、环境/配置问题、权限/外部条件缺失，或尚未查明。归因不清时补查而不是弱化断言；同一问题没有新证据时停止机械重试，改做更小复现、重新诊断或请求必要决定。

节省 Token 的默认动作是：清晰小任务跳过思考；只读相关文件；复用一份任务记录；用稳定 ID 和增量交接；引用命令结果而不复制完整日志；不重复广播未变化的问题；不轮询等待；只在证据触发时升级模型或重新审计。节省 Token 不能删掉用户原文、硬约束、关键差异、失败证据或版本绑定。

最小验收场景：

1. **清晰小改动**：主控定界/基线 → 直接冻结契约 → 执行 → 版本冻结 → 独立审计。
2. **公共契约有歧义**：主控定界 → 按需思考只读决策 → 契约冻结；思考不写代码。
3. **执行发现越界**：提交 `DESIGN_QUESTION`；只暂停依赖路径，主控决定契约回流、等待用户或继续独立工作。
4. **审计拒收**：固定问题和证据 → 执行返工或补证 → 新版本/同版本重新验证 → 独立复审；审计员不修复后自批。
5. **高风险语义审计**：仅因架构、安全、公共契约或最终门禁的明确证据升级到 `max`，不得因任务“大”或一次普通失败自动升级。

本流程通过不自动触发 Git 暂存、提交、推送、部署或外部系统操作；交付必须说明实际完成、修改文件、验证命令/结果、证据位置和未验证项。
