# `context-lean` 条件伴随能力开发文档

> `CONTEXT_COMPANION_REV: v1.0`
>
> 本文是 `multi-agent-dev` 的可选上下文治理扩展。它不覆盖用户最新要求、项目规则、开发文档、章节门禁、权限边界或 `multi-agent-dev` 的角色、范围和审计规则。

## 1. 目标与非目标

`multi-agent-dev` 负责范围、职责、写入权、纠偏和证据验收；`context-lean` 只负责长任务中的上下文膨胀控制、状态保存和压缩后恢复。两者保持分离：主 Skill 负责判断是否需要，伴随 Skill 负责执行上下文治理。

本扩展要解决：

- 大文件、长输出和重复读取造成的上下文膨胀；
- 压缩前没有保存任务状态，压缩后凭记忆继续；
- 压缩或换回合后遗忘契约、写入者、审计状态和下一步；
- 上下文退化后重复探索、无新证据重试或方向漂移。

本扩展不做：

- 不改变用户目标、开发文档、契约、验收标准或模型路由；
- 不新增常驻 Agent，不因上下文问题自动创建替代写入者；
- 不把 `context-lean` 的平台专属命令、Hook、阈值和性能数据变成通用硬规则；
- 不把状态快照当作代码完成、测试通过或审计放行证据。

## 2. 条件启用契约

主控在建立基线后记录 `CONTEXT_MODE`，取值为：

```text
NOT_NEEDED  清晰、短小、低读取量任务，跳过伴随能力
ARMED       预计较长或材料较多，采用轻量上下文纪律，等待风险信号
ACTIVE      已出现膨胀、退化或压缩需求，读取并执行 context-lean
BLOCKED     状态无法可靠保存或恢复，暂停受影响路径
```

满足任一条件时至少进入 `ARMED`：

- 预计多轮连续开发、跨多个模块或多个子智能体交接；
- 需要读取大量文件、长日志、批量数据或大规模搜索结果；
- 同一材料被重复读取，出现遗忘、引用错文件、重复解释或无新证据重试；
- 平台提示接近上下文限制，或即将使用压缩/新回合恢复。

出现明确压缩需求、退化信号或恢复动作时，主控才将其提升为 `ACTIVE`。小任务不得为了“保险”强行启用全部压缩流程。

平台支持按 Skill 路由时，`ACTIVE` 应读取并执行 [context-lean/SKILL.md](../../context-lean/SKILL.md)；不支持递归加载时，使用本文第 3～5 节的最小规则并如实说明，不得声称已执行未被平台支持的 Hook 或命令。

## 3. 最小上下文纪律

`ARMED` 或 `ACTIVE` 时，主控和子智能体共同遵守：

1. 先用定位、搜索和分段读取，再读取必要片段；未改变的文件不重复全文读取。
2. 超长命令输出、日志或样本落到项目允许的证据文件，只在交接中保留路径、摘要、错误位置和退出码；错误、差异、回滚步骤不能被摘要删除。
3. 复用 `multi-agent-dev` 的一份任务记录，不强制另建第二套台账。至少同步目标、当前文件、契约修订、关键决策、阻塞、下一步、唯一写入者、审计状态和版本标识。
4. 在基线、契约冻结、里程碑、版本冻结和审计交接后更新检查点；状态变化或证据变化才更新，不搬运完整会话和日志。
5. 工具调用和重试只作成本信号，不设跨项目的固定次数上限；同一失败没有新证据时停止机械重试并重新归因。

用户明确要求完整输出时，用户要求优先；瘦身只去除重复内容，不去除能证明合规或定位失败的证据。

## 4. 压缩门禁

只有同时满足以下条件，才允许主动压缩或切换到需要恢复的回合：

1. 当前写入、测试和审计动作已到安全边界，没有未记录的进行中操作；
2. 任务记录已保存当前目标、修改文件、契约版本、开放问题、写入者和下一步；
3. 工作区差异、送审版本和关键验证结果可重新核对；
4. 平台确实支持所采用的压缩命令或 Hook，或主控已明确改用手工状态恢复。

以下情况禁止压缩后直接继续写入：正在编辑/测试、写入者状态未知、版本尚未冻结、审计证据未绑定版本，或任务处于 `ORCH_STOP_REQUESTED` / `ORCH_BLOCKED_NEEDS_USER`。

`/compact`、`PreCompact`、`SessionStart(source=compact)` 等名称只在目标平台已确认时使用。不能把某个平台的上下文百分比、耗时、缓存行为或 Hook 输入输出推断为所有平台的事实。

## 5. 恢复门禁

压缩、清理上下文、切换回合或重新打开任务后，主控必须先恢复并核对：

1. 用户目标、非目标和原文硬约束；
2. 当前 `CONTRACT_REV`、基线、实际修改文件和送审版本；
3. 唯一写入者、`WRITER_STATUS`、`AUDIT_OWNER` 及停止/交接证据；
4. 已完成验证、开放问题、下一步和受影响的依赖路径。

恢复记录缺失、过期、与工作区不一致或无法确认写入者时，进入 `BLOCKED`，重新基线或请求用户决定；不能凭压缩摘要直接继续写代码，也不能把恢复成功当作审计通过。

上下文治理发现主回合或旧写入者停滞时，仍必须遵守 `ORCH_STALE_SUSPECTED`、`ORCH_STOP_REQUESTED` 和 `ORCH_BLOCKED_NEEDS_USER` 的既有收敛规则。`context-lean` 无权绕过停止确认、唯一写入者门禁或替代 Agent 派发门禁。

## 6. 四种职责的边界

| 职责 | 上下文治理职责 | 禁止事项 |
| --- | --- | --- |
| 主控 | 判断 `CONTEXT_MODE`，安排检查点和恢复，决定是否读取伴随 Skill | 不因压缩方便而扩大范围、替换写入者或降低验收 |
| 按需思考 | 在上下文退化、恢复冲突或材料过大时给出最小处理决策 | 不保存隐藏推理，不以“节省上下文”为由改公共契约 |
| 执行 | 遵守精准读取、输出留证和检查点，报告恢复后的实际差异 | 不在写入中擅自压缩，不凭摘要补造代码或需求 |
| 独立审计 | 检查状态是否对应最终版本，确认压缩后没有丢失约束和证据 | 不修改状态、代码、测试或用快照替代审计 |

## 7. 验收矩阵与 Exit Gate

| 场景 | 预期行为 | 必要证据 |
| --- | --- | --- |
| 清晰小任务 | `CONTEXT_MODE=NOT_NEEDED`，不加载伴随 Skill | 任务记录中的复杂度判断 |
| 长任务/大读取 | 进入 `ARMED`，执行精准读取和输出留证 | 检查点、证据路径和摘要 |
| 需要压缩 | 进入 `ACTIVE`，先保存状态再压缩 | 压缩前状态、平台能力或手工恢复记录 |
| 压缩后恢复 | 先完成恢复门禁，再允许写入 | 契约、基线、写入者和下一步核对记录 |
| Hook/命令不可用 | 不伪称自动保存或恢复，改用可验证替代方案或阻断 | 能力探测结果与缺口 |
| 写入者停滞 | 沿用协作停滞门，不 fork、不接管、不继续写 | 状态快照、停止请求和复核结果 |
| 用户要求完整输出 | 保留完整输出，不强制瘦身 | 用户请求与实际交付 |

本扩展文档级完成的最低条件：主 Skill 已加入条件触发和恢复门禁；本开发文档与独立契约测试已更新；契约测试覆盖“不启用、启用、不可用、恢复和停滞优先级”的规则存在性与关键顺序；没有把平台专属阈值或 Hook 声称为普遍能力。真实平台的递归 Skill、压缩命令和 Hook 生命周期仍需在目标环境单独验证，不能用本文测试伪称已验证。

## 8. 兼容与迁移

现有只调用 `multi-agent-dev` 的任务仍可运行：短任务默认不增加步骤，长任务由主控按条件启用 `context-lean`。已有单独安装的 `context-lean` 仍可直接使用；本扩展只是提供主 Skill 的自动路由和边界，不复制或取代其详细规则。修改 Skill 后按目标平台要求重新加载或重启，不能假设已经运行的主会话会自动切换到新规则。
