# 多 Agent 协作开发

以最少协作成本实现：文档定范围，主控管边界，按需思考解决歧义，执行做最小改动，独立审计凭证据放行。

采用“四种逻辑职责、一份任务记录、事件驱动四步流程”。四种职责不等于四个 Agent 常驻；清晰小任务不启用思考 Agent，主控通常就是当前会话，也不得再派生一个主控 Agent。不要把流程扩成常驻的产品、架构、测试、审计等多层组织。

## 1. 使用边界与四条原则

遵守当前指令优先级、项目 `AGENTS.md` 及相关开发文档。本 Skill 只补充工作方法，不覆盖项目的范围、章节、审批或验收规则，也不自动授权提交、推送、部署、付费调用或操作外部系统。

先识别用户是在要求实施，还是说明、诊断、评审。后者保持只读，不因加载 Skill 就改代码。已有文档和授权足够时直接推进；只有影响范围、业务规则、硬约束或外部权限的缺口才向用户确认。

将“八荣八耻”落实为四条操作原则：

1. **查实并对齐**：先查接口、代码与文档，不猜接口、不模糊开工；业务规则不明时说明缺口，不脑补业务。
2. **守界并复用**：优先使用语义合适的已有实现、类型、变量与测试，不新增冗余、不随意改架构；复用不是跨模块越权或强行拼接。
3. **验证并诚实**：准备必要的正常、失败和边界验证；明确区分已观察、推断、未验证，不用口头保证代替证据。
4. **小步并纠偏**：按可验证的最小任务推进，每步检查范围和约束，不顺手扩功能、不做无关批量改动。

“严格不新增变量”“必须原样复用来源逻辑”等是用户或项目给出的任务约束，不是所有项目的默认禁令。不得把示例变成通用限制，也不得擅自弱化当前任务真正的限制。

## 2. 四种职责与协作边界

| 职责 | 负责 | 不得做 |
| --- | --- | --- |
| 主控 | 读取依据，冻结范围、基线和当前状态，决定下一责任人及是否升级，协调冲突，集成并交付；通常是当前会话 | 自行扩大需求、豁免硬约束、再次派生主控，或以“多数 Agent 同意”代替证据 |
| 按需思考 | 只读处理需求、架构、契约和验收歧义，输出可执行决策、选项和风险 | 写代码、改测试、替用户扩范围、要求或保存隐藏推理；清晰小任务不启用 |
| 执行 | 在冻结契约和唯一写入边界内实现、定向测试，允许实现层局部推理并提交实际差异和证据 | 改变公开 API/schema/状态/事件/安全/权限/持久化/外部副作用语义，增加需求、平行逻辑、兼容路径或验收标准；越界先发 `DESIGN_QUESTION` |
| 独立审计 | 对固定版本直接对照要求、基线、差异和可观察证据，检查功能、边界、硬约束和是否过度开发 | 修改被审代码、测试或验收标准来制造通过，要求或声称看到隐藏推理，或照抄执行者结论 |

- 小任务：主控可兼执行，另设独立审计；明确无歧义时跳过按需思考。可拆分任务：主控、执行、审计；只有存在真正独立的产出才派执行 Agent，不为凑职责开 Agent。
- 根因不清且有可独立调查的部分时，可先派只读调查任务，返回调用链、失败归因证据和建议改动范围；调查不新增常驻职责，也不自动获得修复权限。
- 有可用子智能体工具时，主控将具体、有边界的工作委派给子智能体，同时推进本地的契约核对、验收准备或集成工作。不要用新建侧边栏会话代替子智能体，除非用户明确要求独立会话。
- 每个开发任务必须指定唯一写入负责人。共享文件、接口定义、测试数据库、端口和夹具也要明确所有权；会互相干扰的工作串行进行，或使用独立工作区与资源。
- 下发任务时给出目标、依据路径/章节、允许改动、原文硬约束、基线、依赖和验收方法。子智能体先阅读相关原文；只执行分配的职责，不自行递归扩编团队。
- 独立审计必须与被审改动的作者分离，包括主控写入的集成改动；审计可运行安全验证，但不得修改被审对象。若运行环境支持只读权限或隔离工作区，可据此限制权限；仅写“只读”不等于已经有技术隔离。
- 子智能体工具不可用时，明确说明只能自检。可以推进仍被授权的工作，但不得伪称独立审计完成；独立审计是本次必需条件时，不得宣布验收通过。

### 2.1 参考文档的阅读路由

完整执行细则见 [references/adaptive-four-role-workflow.md](references/adaptive-four-role-workflow.md)。实际启动多阶段/多 Agent 实施、需要模型路由、契约修订或失败回流时，必须完整阅读该文档；仅做概念说明、只读短评或单一清晰小任务时可不加载全文。参考文档只解释协作方法，不覆盖项目规则、用户授权、章节门禁或外部操作边界。模型路由硬门禁、`MAD_ROUTE_V1` marker、Hook 输入输出和验收矩阵见 [docs/model-routing-hard-gate-development.md](docs/model-routing-hard-gate-development.md)；凡启用派发门禁，先按该开发文档冻结契约。

## 3. 一份任务记录

优先复用项目现有任务单、章节记录或审计记录，不再建立重复台账。没有现成载体时，按规模使用一份简短文件或会话中的结构化记录。最少包含：

```text
目标与范围：本次用户结果；明确不做什么；允许改动的文件/模块。
依据与约束：要求的原文及位置；C1、C2…硬约束的对象、范围、检查方法。
分工与依赖：每项任务的负责人、写入边界、共享资源及前置条件。
版本与基线：起始提交和已有未提交改动；待审改动的提交/补丁及必要文件哈希。
门禁与交接：`CONTRACT_REV`、`COMPLEXITY_GATE`、当前唯一写入者、`WRITER_STATUS`、`AUDIT_OWNER` 及停止/交接证据。
验收与证据：R1、R2…成功条件；测试、反例、约束检查的预期与实际结果。
状态与问题：当前步骤；问题编号、证据、责任人、下一步；最终未验证项。
```

保留用户要求原文，不能只保存主控的改写。允许修改某个文件，不代表允许在里面新增任意行为。未来路线图、历史方案和“顺便优化”不构成本次授权。

## 4. 事件驱动四步流程

事件驱动表示主控在每个有意义的交接、决策、差异、审计结论或阻断条件出现后选择下一状态和责任人；它不是软件事件系统，也不是定时轮询。最小状态流为：

```text
定界/基线 → 必要时思考 → 契约冻结 → 执行 → 版本冻结 → 审计
                                      ├→ 通过
                                      ├→ 实现返工
                                      ├→ 补证
                                      ├→ 契约回流
                                      └→ 等待用户
```

清晰小任务可由主控直接从定界/基线进入契约冻结；只有需求、架构、公共契约或验收存在实质歧义时才触发按需思考。

### 第一步：定界与建立基线，必要时思考

1. 阅读相关项目规则、当前任务文档、契约和既有实现；用 `rg` 等定位类型、变量、入口和测试。只加载与当前任务有关的材料。
2. 检查工作区状态，记录起始提交及相关的未提交、未跟踪文件；已有用户改动属于基线，不能覆盖或冒充本次成果。无 Git 时用相关文件快照或哈希建立可比对基线。
3. 把范围、硬约束和验收方法记入任务记录。每条硬约束对应明确的检查对象和方法；检查方法不能替换或缩窄用户原意。
4. 文档冲突、规则歧义或目标与禁令不兼容时，先定位原文和最小冲突，再请求必要决定。不得擅自新增例外；清晰且可执行的任务无需反复等待确认。
5. 主控把是否启用按需思考作为一次状态决策；思考只返回最小可执行决策和未决问题，不写代码、不改变用户范围。

### 第二步：冻结执行契约，最小实现与持续纠偏

1. 在派发执行前冻结目标、非目标、允许文件/模块、唯一写入者、公共契约不变量、依赖、验收证据和版本标识；执行者先逐项核对再动手。
2. 按依赖顺序实施，每个任务只产生一个可独立验证的结果。新增或修改的行为必须对应本次要求，或有可解释的必要支撑关系。
3. 每轮小改动后比较任务范围、硬约束和实际差异。不能等全部开发完才检查跑偏。执行者报告改了什么、为何必要、验证了什么及尚存疑点。
4. 执行中的局部推理只能服务于实现和调试，不得改变公开 API/schema/状态/事件/安全/权限/持久化/外部副作用语义；发现越界立即发 `DESIGN_QUESTION`，只暂停依赖该决定的路径。
5. 发现越界、违约或依据缺失时，停止问题扩散和依赖它的后续推进，记录具体差异和要求位置，由责任执行者在授权范围内修正；这不禁止纠正工作，无关且仍可安全推进的任务也可继续。
6. 需要扩展范围、调整公共契约或放宽限制时，先取得必要授权并更新任务依据，再实现和重审。审计员不能因为“这样更好”自行批准改需求。
7. 不顺手重构、升级依赖、重命名、增设配置或补未来功能。新的改进建议只记录，不当作已获批准的开发任务。

失败先归因再决定怎么修：结合可比环境下的基线对照、最小复现和现行契约，区分本次回归、既有缺陷、夹具/断言与契约错位、环境/配置问题和尚未查明，并在同一任务记录注明关联范围、证据及局限。基线也失败不等于与本次无关；归因不明先补查，不能凭“测试过时”弱化断言。仅修授权范围内的问题，无关失败记录后另行定界；影响必需验收的历史或环境失败仍不能豁免。

### 第三步：固定版本，独立凭证据审计

执行者送审时提供完整的任务差异、基线、验证记录和已知问题。版本冻结后暂停对被审对象的写入，或提供不可变补丁/提交和必要文件哈希。起始工作区不干净时，不能只把 `HEAD` 当作完整基线。

审计员自行读取要求原文和实际差异，必要时复跑测试，不依赖执行者的合规声明。不得要求或声称看到隐藏推理；把过度思考转化为可观察检查：额外文件、抽象、字段、变量、方法、依赖、重命名、行为，以及无新证据的重复尝试。检查范围包含本次实现、测试、相关生成文件与集成改动，并确认未破坏起始用户改动。

逐条记录证据，不要求重复粘贴完整日志：

| 要求 ID 与原文位置 | 检查对象与方法 | 实际证据 | 对应版本 | 结论 |
| --- | --- | --- | --- | --- |
| C1 / R1 | 文件、符号、差异、命令或复现步骤 | 预期与实测、退出码、必要日志/产物位置及覆盖局限 | 基线与待审版本标识 | 符合 / 不符合 / 证据不足 |

关键审查规则：

- **范围合规**：将新增和修改的行为映射到已批准的要求；只有功能测试通过，不能证明没有额外功能。
- **实现方式合规**：验证用户指定的方法，不能仅验证结果“看起来一样”。“严格不新增变量、不改名”须在约定范围内比较前后声明、符号及引用；按语言使用现有编译器/AST 工具或逐项差异审查，结合行为检查，不自行引入通用扫描器或新依赖。
- **禁止偷换检查口径**：变量总数不变，不能证明没有新增或改名；不能自行排除局部变量、测试代码、配置字段，也不能用动态属性、别名、生成代码等绕过实质限制。原要求的适用范围不清时回到定界步骤。
- **功能确实完成**：验证正常路径和必要的失败、边界、回归路径。记录执行环境、真实命令和结果；未运行、跳过、环境失败和测试不覆盖，不能包装成通过。
- **证据与版本绑定**：审查后有改动，重新审查受影响项及依赖项；范围不明时扩大复核。禁止用旧版本绿灯批准新版本，也不无理由全量重跑。
- **结论不夸大**：测试通过不等于所有约束成立；多个同模型 Agent 的一致意见也不是证明。证据含敏感信息时先脱敏，再保存或引用。

结论只有“符合”“不符合”“证据不足”。必需项存在“不符合”或“证据不足”时不得通过；后者需要补证，不是自动认定违规。审查意见必须说明违反或缺失了什么，不能凭个人偏好扩需求。

**拒收后的默认动作**：对已授权的实施任务，主控自动组织并自动调度冻结契约范围内的“修正或补证 → 固定新版本 → 重跑受影响检查 → 独立复审”；自动调度只负责责任人和状态路由，不等于审计员自动修复、自行补证或补证后自批。复审通过后再推进依赖任务；只补证未改代码时，也须由独立审计确认同一版本的证据充分。审计员保持只读。只要还有安全、范围内的修复或补证步骤，就继续执行，不因一次拒收再次要求用户说“继续”。只有修复必须扩大范围、改变契约、放宽硬约束或取得新权限时才等待用户；说明、诊断和评审任务不因此获得修复授权。

**确需暂停的边界**：若修复必须扩大范围、改变契约、放宽硬约束或取得新权限，先请求必要决定；若必需的依据、基线或外部条件缺失，先尝试安全且已获授权的补查和替代验证，仍不足时暂停受影响路径。说明问题证据、已尝试的方法、尚缺的具体条件或用户决定，不擅造基线、不降验收标准，也不把未完成目标标为完成。其他独立且安全的工作可继续。

### 第四步：按结论路由，集成复验与交付

审计结论为“符合”才进入通过；“不符合”回到实现返工；“证据不足”回到补证。范围内的修正或补证由主控自动路由给责任执行者并按流程复审，但审计员不得自动修复、自补证后自批。若问题需要改变契约、扩展范围、放宽硬约束或取得权限，回到契约回流或等待用户；只暂停受影响路径。主控集成后，在最终版本验证关键用户流程与受影响回归项；集成改动也需独立审计。满足以下条件才报告完成：用户目标实现、范围合规、硬约束符合、必要测试通过、证据对应最终版本。

安全拒绝、不支持、禁用或等待，可能是正确的边界处理，但不能因此把未实现的目标标记完成；仅当本次目标本身就是拒绝或禁用时，才据其验收条件判断。

交付用简短结果说明：实际完成、修改文件、验证命令和结果、硬约束证据位置、未完成/未验证项及必要决定。项目已有章节状态、审批与提交规则时继续遵守；本流程通过不自动触发 Git 提交或任何外部操作。

## 5. 自适应模型路由、Token 控制与可信度

模型与推理路由、角色默认配置和升级条件见参考文档。入口门禁是：只有显式派发且平台支持时才设置子 Agent 模型/推理强度，不可用时如实披露；不能因“更保险”、普通失败或任务较大自动启用 `max`，也不能自动切换当前主会话模型。

### 5.1 `MAD_ROUTE_V1` 派发硬门禁

对 `Agent`、`spawn_agent`、`multi_agent_v1__spawn_agent` 的派发，启用用户级同步 `PreToolUse` Hook 后，marker 必须是 `message` 第一非空行的单行 JSON，且外层 `tool_use_id`、marker `task_id` 使用安全短 ID、`contract_rev` 精确为当前策略版本。合法组合按开发文档真值表路由：`think + ESCALATE_REQUIRED` 使用 `gpt-5.6-sol/max`，`execute`/`audit + SIMPLE_PROVEN` 使用 `gpt-5.6-luna/high`，`execute`/`audit + ESCALATE_REQUIRED` 使用 `gpt-5.6-luna/max`；`think + SIMPLE_PROVEN` 和角色/阶段不匹配均拒绝。合法输入的 model/reasoning_effort 无论遗漏、错误或 `xhigh` 都由 `updatedInput` 改为真值表值，并在 `hookSpecificOutput.additionalContext` 返回绑定 tool_use_id 的脱敏 `MAD_ROUTE_RECEIPT`；非法 marker、字段、阶段、Agent 类型、task_name 或全历史 fork 同步 deny。没有 marker 的普通 spawn 必须 stdout 为空、退出 0，不影响其他 Skill；以 `madv1_` 开头的 task_name 缺 marker 时拒绝。

Hook 只兼容内置 `worker`、`explorer`、`default`，不建立自定义 Agent 配置；当前 schema 的 task_name 必须已经匹配与 marker 一致的 `madv1_<role>_<simple|escalate>_<slug>`，不得自动改写，缺失 `fork_turns` 可补 `none`，`all`、正整数、字符串正整数及其他值拒绝；旧式显式 `fork_context=true` 拒绝，`false` 保留，`fork_turns` 与 `fork_context` 同时出现的混合 schema 直接拒绝，无法识别的 schema 不盲加字段。每次人工或程序派发仍必须显式提供目标 model/reasoning_effort 和适用平台的非继承 fork，即使 Hook 会做最小校正；缺 marker/receipt、出现 `xhigh` 或实际路由不符，结果不得放行。

用户级 Hook 需要重启 Codex 并通过 `/hooks` 审阅、信任；未信任或未重启时硬门禁不生效，工作流必须 fail-closed。配置不使用全局 `[agents].default_subagent_*`，以兼容本机桌面与 PATH CLI；省略参数时 Luna High 主控继承只作兜底，复杂主控下遗漏不能放行，Skill 仍要求显式参数、marker 和 receipt。Skill 不能自动切换已经运行的主会话模型，也不能声称 receipt 证明下游实际采用模型；启动时无法证明主控为 Luna High/Max，应披露并在正确配置的新任务继续。若错误 Agent 已启动，先安全停止并确认 `inactive`/`completed`/`failed` 且无进行中写入，再按正确 marker、路由和 fork 重新派发。

**保守升级门禁**：在契约冻结前，主控必须记录 `COMPLEXITY_GATE`。只有同时证明任务是单模块局部改动、需求和验收无歧义、不涉及公共 API/schema/状态/事件/安全/权限/持久化/外部副作用、没有跨模块依赖或设计问题时，才允许按 `Luna High` 启动执行。任一条件不满足或无法证明为简单任务，必须先升级：设计/语义问题启用唯一的 `gpt-5.6-sol/max` 思考 Agent；契约已冻结但实现、调试、阶段门禁或审计复杂时，将主控/执行/审计从 `gpt-5.6-luna/high` 升为 `gpt-5.6-luna/max`；不得在未完成升级判断前以 `Luna High` 继续实现。平台不支持目标配置时如实披露并使用可用配置，不得伪称已升级。

- 纠偏和质量审计归入同一独立审计职责，使用同一任务记录；设计讨论与纠偏可早介入，正式验收只针对固定版本。
- 问题使用稳定编号，只有状态或证据变化才更新；不重复广播相同警告，不互相轮询催进度，不把长日志搬来搬去。
- 只传交接所需的最小增量：稳定 ID、契约修订、版本、需求 ID、证据、开放问题和下一责任人；不复制全会话或全日志。优先复用同一上下文和一份任务记录，清晰小任务跳过思考，只有新证据才触发升级。
- 同一问题反复失败且没有新证据时，停止机械重试，缩小复现、重新诊断或改用有依据的方法；仍有安全且获授权的下一步就继续，确需暂停时按上述边界处理，不套用固定重试次数，也不为结束任务降低标准。
- 任务连续且上下文仍可靠时，优先延续原执行者，避免反复换人重查。重分配写任务前必须按“停止/中断原写入者 → 使用平台状态工具确认其为 `inactive`/`completed`/`failed` 且没有进行中的写入 → 记录 `WRITER_STATUS` 与停止证据 → 再派新的唯一写入者”执行；停止调用失败、状态未知或旧写入者仍活动时，禁止派发替代写入者，只能等待、补查或请求用户决定。不能把“额度耗尽”、口头说已中断或一次失败消息当作停止证据。禁止两个 Agent 同时“接管”，也不能让执行者以换角色代替独立审计。完成交付后收束任务，不自建无限审计或自动跟进循环。
- 任何版本在进入 `ACCEPTED` 前，必须有固定版本、完整验证和独立 `AUDIT_OWNER` 的审计结论；执行中、测试失败、版本未冻结或审计未完成时，只能保持进行中/阻断，不能提交、推送或宣布完成。
- Skill 是操作指引，不是强制权限系统。可机器判定的关键限制应优先使用项目已有的静态检查或 CI；新增门禁本身也必须在授权范围内。无可执行检查时如实说明审查方法和局限，不承诺零偏航或绝对证明。
